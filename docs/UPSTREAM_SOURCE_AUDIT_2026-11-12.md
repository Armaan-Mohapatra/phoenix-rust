## Status definitions

- **DIRECT_INTEGRATION**: a pinned original upstream source dependency is compiled and used by tests.
- **PORT_TO_RUST**: a legally reviewed public mathematical concept has an original Rust implementation with tests; upstream runtime is not linked.
- **TEST_REFERENCE**: read specific upstream implementation or tests, design/tests useful, but **not integrated**.
- **SOURCE_ONLY**: code exists, not yet justified for direct adoption.
- **BLOCKED**: licensing, source, runtime, safety or functionality prevents adoption.
- **EXCLUDED**: out of scope.

## Source compatibility and priorities

- Phoenix's *binary* venue book has YES/NO resting bids; YES ask=10000−NO bid (in 1e-4 dollar price units). HftBacktest assumes conventional bid/ask and f64 order sizes; the adapter tests exactly one resting YES queue without handing accounting to upstream.
- The HftBacktest dependency is Rust `edition=2024`, `rust-version=1.91.1`, so it is deliberately outside Phoenix's older `rust-version=1.78` workspace; Windows native MSVC remains a local deployment blocker despite hosted CI success.
- None of the above projects authenticates Phoenix's historical CF reference-index ticks, proves market/rules identity, replays full actual Kalshi+Perps archives or establishes realistic maker fills from historical L2.
- High return on next integration effort: **Oracle3 effective-dated series fee input**, **Octagon event-clustered bootstrap**, **Jon-Becker trade/market cursors**; Tarp risk guard was ported as a tested isolated prototype, still needs lifecycle/ledger wiring.
- Avoid launching upstream bots, pulling bulk upstream datasets, copying private credentials, rebuilding production, or counting cross-platform paper execution as verified realized P&L.
